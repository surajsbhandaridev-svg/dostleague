# DostLeague (v9)

Daily challenges, live friend battles (Socket.IO), leaderboards, friend challenges and moderated community submissions.
Browser → Render static site (React/Vite) → Render web service (Express + Socket.IO) → Supabase PostgreSQL.

> **Validation note:** the supplied ZIP has no `package-lock.json`. I attempted to install dependencies in the review environment, but its DNS could not resolve `registry.npmjs.org`, so I could not run the full build or automated tests here. The deployment commands below use `npm install --include=dev` to avoid the immediate `npm ci`/missing-lockfile failure. Please run the checks locally before relying on a public deployment.

## Local setup (Windows PowerShell)
1. Install Node.js 20+ and Git (`winget install OpenJS.NodeJS.LTS Git.Git`), then reopen PowerShell.
2. `npm install --include=dev` (from repo root). This creates `package-lock.json`; keep that file and commit it to GitHub. Once the lockfile is committed, you can switch Render build commands to `npm ci --include=dev` for repeatable installs.
3. Supabase: create a project → open **Connect** → select **Session pooler** → copy the entire PostgreSQL URI. Use the exact pooler hostname and username from the dashboard; do not manually construct `db.<project-ref>.supabase.co`.
4. `Copy-Item backend\.env.example backend\.env` and `Copy-Item frontend\.env.example frontend\.env`. In `backend\.env` set `DATABASE_URL` and a random `SESSION_TOKEN_SECRET` (at least 32 characters). `ADMIN_API_KEY` is commented out by default; uncomment it with a random value of at least 24 characters only if you want the moderation screen enabled. Do not place database credentials in frontend environment variables.
5. `npm run db:migrate -w backend` then `npm run db:seed -w backend` (365 days of packs starting today, IST). These commands now build the shared workspace first.
6. Terminal 1: `npm run dev:backend`. Terminal 2: `npm run dev:frontend`. Open http://localhost:5173.
7. Two-player test: open the site in a normal window and a private window (separate guests), create a room in one, join by code in the other, ready up, start.
8. Tests/build: `npm test` (backend), `npm test -w frontend`, `npm run build`.

## Deploy (Render + Supabase, free plans)
1. Push to GitHub (never commit `.env`). Render → New → Blueprint → pick the repo (`render.yaml`).
2. Backend env: `DATABASE_URL`, `ALLOWED_ORIGINS` = your exact static-site URL, `SESSION_TOKEN_SECRET` (auto-generated by the Blueprint), and `ADMIN_API_KEY` (the Blueprint prompts for this value; enter a unique random value of at least 24 characters to enable `/admin`).
3. Frontend env: `VITE_API_BASE_URL` and `VITE_SOCKET_URL` = the backend `https://….onrender.com` URL; `VITE_SITE_URL` = the static site URL. Redeploy after changing (Vite bakes them in at build time).
4. Run migrate + seed once from your PC against the Supabase `DATABASE_URL`. The seeder creates a rolling 365-day horizon; rerun the seed script when you want to extend the horizon.
5. Verify: `https://<api>/health` and `/health/ready` return ok; play a Dangal; restart the backend service in Render; the leaderboard still shows your score.

## Free-plan limits
Render free services sleep after ~15 min idle (≈1 min wake) and have no persistent disk; a sleeping or restarted backend interrupts live rooms (the UI says so, and no winner is invented). Supabase free projects pause after a week of inactivity and have usage limits. We do not add keep-alive pings. Not suitable for guaranteed uptime.

## Status
Built: guest play, optional email/password account creation/sign-in (guest profile can be upgraded to preserve existing player history), Daily Dangal, practice (personal history saved; never ranked), live rooms with 11 modes (adds **Math Rush**, **Odd One Out**, **Word Scramble**) (Today's pack, Quick Trivia, Emoji, Guessing, Pattern, Memory with the sequence hidden after 4 s, Community challenges, **Caption Battle** = write captions, anonymous voting, no self-votes, 100 points per vote), results with explanations, leaderboards (daily, weekly, all-time, friends, **by category**), challenge links, history, moderated community submissions (playable), achievements, profiles, public pages, optional consent-gated ads. Room metadata (code, host, mode, status, players) is saved to Postgres whenever it changes; on boot, rooms left over from a previous process are marked voided.
**Not built:** running more than one backend instance (needs a Socket.IO Redis adapter and shared room state, see docs/architecture.md); profanity filtering for captions beyond moderator review of community submissions (captions in live rooms are not moderated; rooms are private).
**Tests written, none run by the author** (no network): backend unit/socket tests (incl. reconnect, caption battle, persistence), frontend component tests, `e2e/battle.spec.ts` (Playwright).
Run `npx playwright install chromium` once before `npm run e2e`. Apply all migrations, including `007_accounts_and_solo_results.sql`, with `npm run db:migrate -w backend`.

See `docs/` for architecture, security and troubleshooting.

## AdSense readiness (see ADSENSE_READINESS_REPORT.md)
Ads are **off by default** and nothing guarantees approval. Ads can only appear on three long editorial articles (`src/ads/policy.ts`); never on gameplay, forms, policy or private pages.
- Preview the layout without real ads: `npm run dev:frontend` then open `/ads-preview` (production hides it unless `VITE_ADS_PREVIEW=true`).
- Enable real ads only after AdSense shows the site as **Ready**: set `VITE_ADS_ENABLED=true`, `VITE_ADS_SITE_APPROVED=true`, `VITE_ADSENSE_CLIENT`, and `VITE_ADSENSE_SLOT_GUIDE_TOP/MIDDLE/BOTTOM` in the Render **static-site** environment, then redeploy (Vite embeds values at build time).
- `ads.txt` is generated only from a real `VITE_ADSENSE_CLIENT`. For EEA/UK/Switzerland traffic configure a Google-certified CMP in AdSense (Privacy & messaging).
- Backend secrets (`DATABASE_URL`, `SESSION_TOKEN_SECRET`, `ADMIN_API_KEY`) belong only to the Render **backend** service, never to frontend variables.


## Game library, solo, bots, accounts and Signal Saboteur
- Home page: 13 games with local cover art, filters and a Solo / vs Bots / Friends chooser (`frontend/src/games.ts` is the single source of truth).
- Solo practice and bot matches for 8 quiz modes (`/practice/:mode`) are unranked and, once migration 007 is applied and the database is reachable, saved to personal history. Signal Saboteur vs bots at `/saboteur` also saves completed results to personal history, never the public competitive leaderboard.
- `/account` provides Create account and Sign in. If you are playing as a guest, use Create account to attach an email/password to the same player ID so existing database history stays associated. Signing into a different existing account switches the browser profile; guest history is not automatically merged into another account.
- Live-room results remain separate from solo/bot practice. Bots inside friend rooms and Signal Saboteur with human friends are not implemented unless explicitly listed as supported in the game-mode chooser.
- Regenerate covers: `python3 tools/make-covers.py`.
